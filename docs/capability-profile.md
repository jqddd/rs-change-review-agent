# 算法能力画像规范（v0.1 草案）

> 本文件规定：接入新算法工具时，需附带一份「能力画像」，供后续「多算法择优」调度使用。
> **状态：v0.1 草稿** —— 当前只要求记录「稳定事实」字段；详细的相似度方案（embedding / 参考样例）待老师明确「数据相似度分析」具体做法后，在本文件内补充。
> 与 `tool-contract.md` 的关系：本文件是其**补充**，专注「工具的能力描述与调度元数据」，不重复契约里的接入/结果规范。

## 1. 为什么需要能力画像

老师计划用两种方式决定「选哪个算法」：
- **数据相似度分析**（最近邻：把当前任务和算法库里「最像的」匹配）
- **提示词分析**（LLM 读每个算法的描述来匹配）

两者都需要每个算法**提前提供「能被比对 / 阅读」的信息**，即能力画像。

## 2. 能力画像 = 结构化字段 + 自然语言描述

每个工具需提供两部分：

### 2.1 结构化字段（给「数据相似度分析」）

v0.1 先定这 5 个**稳定事实**（都是算法固有、不会变的属性）：

| 字段 | 含义 | 取值示例 |
|------|------|---------|
| `output_encoding` | 输出编码 | `binary`（0/1）或 `multiclass`（0/1/2） |
| `target_object` | 目标类别 | `building` / `road` / `both` |
| `trained_on` | 训练数据 | `LEVIR-CD` / `LEVIR-MCI` / `CDD` / … |
| `input_size` | 输入尺寸 | `256` |
| `method_family` | 方法家族 | `transformer` / `cnn` / `diffusion` |

> 字段可扩展；但**同一含义必须用同一字段名**（对齐契约第 4 节原则）。

### 2.2 自然语言描述（给「提示词分析」）

统一句式：**功能 + 适用数据/条件 + 输出编码 + 限制 + 成本**。写进工具的 docstring（lagent 会自动喂给 LLM）。

## 3. 示例（ChangeFormer）

```yaml
tool_name: changeformer
capability:
  output_encoding: binary      # 二值：0=不变，1=变化
  target_object: building
  trained_on: LEVIR-CD
  input_size: 256
  method_family: transformer
description: >
  基于 Transformer 的双时相建筑变化检测，输出二值变化掩码（0=不变 / 1=变化）。
  适合检测建筑的新增/拆除，不含道路类别。输入两张 256×256 对齐影像。
```
